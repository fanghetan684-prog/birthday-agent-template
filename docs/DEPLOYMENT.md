# 本地预览与部署

先完成可操作的本地版本，再按用户需要选择分享方式。本说明解释部署边界，不代表仓库已经上线，也不承诺托管服务永久免费。平台费用、配额、访问权限和具体设置应在执行部署时核实。

## 三种方式的区别

| 方式 | 运行什么 | 能否直接让朋友共同签名 |
| --- | --- | --- |
| 本地预览 | 自己电脑上的 `server.mjs` | 本地地址通常只对本机有效；不能据此声称已完成对外共享 |
| 静态托管 | 构建后的网页、图片、音频与脚本 | 不能单靠静态文件获得 Node 后台；需要另接并实际验证共享服务 |
| Node 服务器部署 | `server.mjs` 及其所需数据存储 | 取决于后台与持久存储是否正确部署、配置并通过读写验证 |

浏览器本地存储不会自动在朋友之间同步。一个人在两个标签页看到相同内容，也不足以证明后台共享成功。

## 本地预览

1. 使用 Node.js 24，检查 `package.json` 中的脚本。
2. 缺少依赖时执行 `npm install`。
3. 运行构建和检查，然后启动：

```sh
npm run build
npm test
npm start
```

打开终端实际输出的地址。`tools/build.mjs` 优先读取被忽略的 `config.local.json`，否则读取通用的 `config.json`，再生成 `public/birthday/config.js`；修改配置后重新构建。个人素材建议放在被忽略的 `public/birthday/assets/user/`。

要让手机访问电脑上的预览，还需要实际可达的地址、网络与监听配置。不要擅自开放防火墙、暴露家庭网络或把本机地址当作已部署网址。

## 静态部署

静态方案适合照片、动画、逐张相册、童年对话、纸条蛋糕、礼物图片和可选的浏览器端密封信。它不会自动运行 `server.mjs`。

Agent 应检查构建结果，以代码实际约定的站点入口与资源根路径打包。`public/birthday/` 含生日页配置及相关产物，但托管根目录如何映射必须结合目标环境核对，不能只猜路径。

部署后检查：

- 页面入口、配置、所有照片、音频及礼物路径能正常加载。
- 子目录部署时，资源链接与返回链接仍然正确。
- 手机滑动与点按、图片放大、童年对话、蛋糕与重播可操作。
- 静态模式的签名功能被明确说明或禁用；若连接独立后台，要验证其真实共享行为。

静态托管并不等于私密。浏览器可加载的素材可能被访问者下载；公开仓库和公开站点应分别检查，不要以仓库未提交照片就推断已发布站点也不包含照片。

## 带真实签名后台的部署

使用支持 Node.js 24 的运行环境，执行项目实际的构建命令，并以 `npm start` 运行 `server.mjs`。端口监听、代理设置、环境变量及存储位置应先读实现，再按平台要求配置，不能编造名称。

当前服务器支持以下变量，公开示例见 `.env.example`。运行时应通过系统环境或托管平台的环境变量设置；不要假定普通 `npm start` 会自动读取 `.env` 文件。

| 变量 | 用途 |
| --- | --- |
| `PORT` | 服务监听端口，默认 `3000`；平台要求优先以平台配置为准 |
| `DATABASE_PATH` | SQLite 文件位置；生产部署应指向实际可持久保存的位置 |
| `PUBLIC_ORIGIN` | 对外访问的完整来源，如协议与域名组合，不含路径；用于验证提交来源 |
| `SIGNATURE_INVITE_TOKEN` | 服务端邀请口令；未配置时拒绝签名提交，不放入公开配置和仓库 |

页面通过带 `invite` 参数的入口接收邀请口令，移入当前浏览器会话后从地址栏移除。分享的是有提交权限的入口，应该只发给预期参与者；不要把真实邀请链接粘贴进公开文档。当前实现允许读取签名、仅限制提交，邀请口令不保护相册或其他页面内容。

`/healthz` 可检查服务是否响应，但它不证明端到端签名已经验证。当前服务器最多保留并接受 200 份签名；如需更改，以实际代码与测试为准。

共享签名的最低要求：

1. 浏览器提交到真实服务端，服务端验证输入并保存。
2. 读取接口返回已保存的记录，文本安全显示。
3. 独立浏览器或另一台设备能读取同一条签名。
4. 刷新后仍存在；有必要时验证服务重启后的保留情况。
5. 请求失败时明确报错，不能伪装为“已经共享成功”。

如果当前实现写本地文件，必须判断平台文件系统是否持久，以及重新部署会不会清空。多个实例各写自己的文件不是可靠的共享存储。需要时接入持久卷或数据库，并报告实际采用的方案；不要在未授权时创建付费资源。

本模板不要求为了看照片而建立复杂账号系统。需要保护签名管理、私人内容或访问者身份时，再按实际需求设计服务端权限。

## 密封信如何随站点部署

私人输入保存在被忽略的 `private/card.json`：

```sh
node tools/seal-card.mjs private/card.json
```

生成的 `public/birthday/card-sealed.js` 是部署用产物，默认同样被 Git 忽略。它可以随个人站的部署包提供，但不应因此将私人输入、答案或密钥提交到公开模板仓库。

采用从 Git 自动构建的托管流程时，**被忽略的文件不会因为本地存在就自动上传**。Agent 必须选择实际支持的方式携带加密产物，例如明确核对后的部署包，或安全构建流程；不能在缺少所需文件时宣称密封信已经发布。具体方式以目标平台能力为准。

部署前检查包内文件，而不是只检查源码目录。不要把明文卡片和加密卡片一起发布。使用容易猜测的解锁答案时，浏览器端密文仍可能被离线尝试，不能宣传为强身份验证或绝对保密。

## 公开模板与个人站分开

公开模板仓库应保留可运行的通用演示，不携带真实用户的私人照片、生日信件、礼物信息或服务凭据。个人定制站可以在忽略目录、独立工作副本或专门的部署产物中制作，以实际项目约定为准。

提交前至少检查：

- 私人目录、个人素材、密封信输入及部署专用密文是否被正确忽略。
- `git status` 和待提交差异中没有私人内容。
- 已跟踪文件及历史提交没有意外包含秘密；仅新增 `.gitignore` 不会清除旧记录。
- 配置和文档中没有真实答案、令牌或不必要的个人路径。

若发现已泄露凭据，应停止继续传播，告知用户并按权限处理失效与替换。不要为了“清理”擅自重写公共历史或删除用户文件。

## 费用与发布结论

未获明确授权，不购买域名、开通付费套餐、增加收费资源或调用收费部署操作。若所选环境无法免费完成，需要先说明具体费用与替代方案，等待决定。

实际发布后，报告真实网址、访问范围、构建与部署状态、已完成的浏览器检查，以及共享签名是否真正验证。失败、等待中、仅生成压缩包和本地服务启动，都不能表述为“已经上线”。
